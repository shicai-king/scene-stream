从网络连接到资源管理

多人一起看，
每间房只生成一份画面。

我们的设计重点是：让许多人安全地共享生成结果，同时把资源的分配、使用和回收安排清楚。

本页依据当前代码编写。按钮只演示规则，不连接直播服务器，也不保存弹幕。示例里的房间和消息都是为讲解编造的。

先把项目边界说清楚

模型画什么，与系统怎样让大家一起看，是两件事。

看画面

网页选择房间 → 登记这个观众 → 送出该房间的最新画面。已经开播的房间无需重新加载模型。

发想法

先确认消息属于哪间房 → 通知这间房的人 → 更新待送内容 → 由该房间统一投递。

开一间新房

先拿到可用资源 → 准备生成程序 → 接上画面 → 真正收到第一张图后才算开播成功。

网络与资源的第一条区别

增加观众会增加连接，但不会多生成一份视频。

省下显卡计算，不代表增加观众没有成本。

两个人同时点“开播”

先把资源记为已预留，再开始慢操作。

为什么不能等模型加载成功后才把位置记为占用？

加载期间，第二个申请仍会看到“空闲”，也会使用同一份资源。因此，准备中的房间已经占用容量，尽管它还没有产生第一张画面。

重复点开播、重复发送同一个申请，会不会多占一份？

已经准备中或正在直播的房间，重复开播直接返回当前状态。创建房间的请求还带有自己的编号，同一编号、同一内容重试时返回原来的房间。编号相同但内容不同会被拒绝。这个记忆有数量上限，也不会跨服务重启永久保留。

是否所有事情都必须一个接一个做？

只有共同记录的修改需要短暂排顺序。加载生成程序、接收不同房间的画面、向不同观众发送内容可以分别推进。较慢的图片转换也另行执行。这样，“同时服务”不等于“同时修改同一张资源表”。

许多人同时改变同一间房

每句话都能看见，等待投递的位置只留最新一句。

先后收到两条

前一条继续留在消息区，但标记为“被替代”。下一次只送尚未投递的最新内容。

同一条被重复补发

每条消息带自己的编号。同一编号和内容只返回原结果，不新增弹幕，也不重新排进待投递位置。

前一条已经送出

我们不能收回它。新内容只能在之后送出；因此页面不会承诺每条消息都对应一次完整换景。

每间房各自记住消息、待投递内容和当前生成连接，并且只由该房间的一个发送者送指令。这样，两个观众同时操作时，也不会各自绕过房间管理直接抢着控制模型。

如果等太久，或者发送失败，会发生什么？

待投递内容有有效期，默认 20 秒。取出时如果已经过期，就标记为过期；发送失败会标记为失败。投递成功只代表内容已经交给通道，不代表模型已按它生成出可见画面。

多人连接各自快慢不同

给慢观众留最新画面，不让旧画面越攒越多。

视频可以跳过旧图

实时观看更在意“现在是什么”，所以不把所有过时画面堆起来。每位观众有独立的发送工作，慢连接不会成为所有人的共同等待点。

消息需要维持顺序

消息与状态变化按顺序发送，并设置数量上限。一个观众长期收不过来时，会关闭该连接，让它重新加入并获取当前状态与仍保留的消息，而不是无限积压。

省下的是哪些成本，又付出了什么代价？

同一房间收到的画面只转换一次，再给多名观众使用，减少重复处理。我们把它转成容易交给网页的独立图片，因此可以和消息一起走一个入口。代价是数据量可能比连续压缩视频更大，观看人数上升后仍需要更多网络和转发处理能力。

分清“人还在”与“视频还在”

浏览器一直在线，也不能证明生成程序没有卡住。

为什么不统一设一个等待时间？

加载模型通常比确认一个浏览器还在耗时更长。如果都设得很短，会把正常加载误判成失败；如果都设得很长，离开的观众和卡死的连接又会迟迟不清理。所以各个阶段分别计时，具体值通过配置调整。

已经停止的旧连接，迟到的画面会串进新一轮直播吗？

每次接收画面或报告异常前，服务都会检查它是否仍属于这间房当前使用的生成来源。旧的一轮结束后，迟到的结果不再被采用。网页切换房间时也会区分新旧连接，避免把上一间的迟到画面放到下一间。

资源管理的关键不是开始，而是结束

“已经收到停止请求”与“现在可以再用”必须分开。

自己管理的程序

关闭这间房的旧连接，结束自己创建的生成程序，再启动新的程序。确认已替换且模型重新可用，才把资源交还。整个过程不会按显卡编号去终止其他人的任务。

外部提供的程序

不能假定我们有权重启它，也不能凭“还能回应”就认为历史已经清空。当前实现没有可靠的外部清理办法，所以结束使用后会暂时停用这一份，等待外部管理者处理。

异常结束后，房间会自动恢复直播吗？

系统会尝试自动清理和恢复那份生成资源；故障房间本身保留失败状态，不自动重新开播。恢复成功后，可以再次点击开播。课堂展示时要分清“资源已经恢复”和“这间房已重新直播”。

为什么确认程序已换新，还要等模型准备好？

新程序可能已经能回答简单请求，但还不能生成。只有确认模型可以工作，才能允许再次分配。否则，下一位使用者会接到一个表面正常、实际不可用的资源。

运行环境与故障边界

只有一个对外入口，内部把各间生成程序分开。

为什么总登记者只运行一份？以后怎样扩大规模？

目前可用资源、房间和消息都保存在这一份服务的内存里。如果直接复制成两份，它们会各自认为同一份资源还空闲。当前采用一个总登记者；跨多台机器的共同记录、备用服务和自动接管，都属于以后需要另外实现的工作。

打包运行解决了什么，没有解决什么？

打包固定依赖版本、启动方式和运行边界，减少换环境后“同样代码却跑不起来”的问题。权重和运行数据另放在项目目录。已验证的方案仍依赖固定的绝对路径，移动目录要重新建立环境；它也不能消除显卡、网络或整台机器故障。

展示时讲清“做了”与“测过了”

把设计理由与实际验证，一一对应起来。

已经验证

多人共享与房间隔离

两页观看同一间房，收到画面与消息；其中一页换房，另一页继续。改变甲房内容不会改写乙房的提示词。

已经验证

单路退出后的回收

让我们管理的一个生成程序意外退出，系统检测并恢复该资源，另一间持续生成；随后重新开播成功。

尚未验证或未实现

更大的运行规模

更多真实生成房间、更高画质和长时间连续运行尚未验证。账号权限、历史持久保存和跨机器接管尚未实现。

课堂上可以这样顺着讲

我们先把“生成一间房”和“观看一间房”分开。增加观众只增加连接，不重复启动模型。新房间先预留资源，防止同时申请重复占用；加载模型时不占着登记入口。多人发来的想法都展示，但等待投递的内容只留最新一句。每位观众独立接收最新画面，慢连接不会把所有人一起拖住。最后，停止请求先进入清理，只有生成程序已换新、模型已准备好，资源才会重新开放。
老师问：“你们的工作量体现在哪里？”

可以沿着几个具体问题回答：多人共看时如何只生成一份；同时开播如何避免重复分配；重复消息如何不重复出现；慢观众如何不积压；退出观众为何不结束房间；失败资源为何不能立即复用。每个问题都有代码中的处理规则，也有相应验证。模型本身的训练和生成算法不计作我们的实现成果。

老师问：“为什么不用更复杂、更大规模的方案？”

这次目标是让自己的电脑稳定演示真实双路互动。一个统一登记者、独立的生成程序、只保留最新画面，已经能覆盖当前场景。我们清楚它仍有共同入口和单台服务器的限制，把进一步扩大规模列为后续工作，而不把尚未实现的能力写成已有功能。
