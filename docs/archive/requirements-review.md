## 1. 已确认的目标

- 用于课程演示，开发在本地，运行文件放在用户指定的远端目录。
- 用户已指定 SSH 主机与可用的 GPU 0–3；具体部署信息保存在不纳入版本控制的 `deployment.local.md`。
- 网页左侧选择直播间，主区域播放所选直播间的视频，并显示提示词弹幕。
- 同一直播间的参与者共享同一条生成视频，进入房间的人均可发提示词。多人观看不能被实现成每个观众另开一份模型推理。
- 提示词策略已确认采用“优先最新”：所有被接受的提示词显示为弹幕，旧的未投递指令被最新指令替代。
- 默认演示两个独立的生成房间；数量可配置，不作为业务硬上限。真实两路并发是本次演示目标。
- 画面清晰度可以让步，优先连续生成和及时响应。具体生成帧率、播放帧率和提示词响应时间必须实测。
- 只需要用户自己的电脑能访问；不需要公开网站、正式账号、计费或 Kubernetes。
- 本地进行 Git 版本管理，未来由用户开源到 GitHub；当前没有发布远端仓库的要求。

## 3. 共享直播间必须改变的语义

原有 `session_id` 同时承担模型生成、浏览器连接和租约生命周期，不能直接覆盖共享直播间。

建议明确以下对象：

| 对象 | 职责 |
|---|---|
| Room | 稳定房间 ID、显示名称、当前提示词、生成状态、参与者数量 |
| GenerationSession | 一条持续生成任务及其 Worker 绑定；同一房间的观众共享该任务 |
| ViewerConnection | 单个浏览器的加入、媒体连接、观测指标、心跳与离开 |
| PromptEvent | 弹幕内容、发送者标识、消息幂等标识、服务端顺序号、投递状态 |

必须满足：

1. 加入已有房间不消耗新的 GPU 生成槽位；容量统计生成任务，另行统计观众数与媒体连接数。
2. 单个观众离开、刷新、掉线或切换房间，只回收该观众连接，不关闭其他人正在看的生成任务。
3. 提示词经服务端统一接收、去重、排序并广播弹幕。原来每个浏览器自行递增同一个 `client_seq` 的规则会产生跨客户端冲突，不能原样使用。
4. 由服务端为房间维护统一的上游控制通道。浏览器的 HTTP 提交不再要求该观众自行向 Scope 二次投递，以免同一房间出现多个相互竞争的控制源。
5. 媒体必须从同一条生成输出分发。需实测 Scope 能否直接共享输出；若不能，增加服务端媒体接收与分发层。不得假设每个新 offer 都是在观看同一条生成任务。
6. 房间列表需要返回显示名称、状态等侧栏所需信息。现有 Session schema 未定义 `label` 返回字段。
7. 增加房间列表/详情、观众加入/离开、发送消息、房间事件订阅与重连同步的契约。现有 v2 没有相应接口。
8. `ACCEPTED` 表示已登记；服务端已发送上游与画面已经生效仍是不同事件。没有可靠上游 ACK 时，不宣称模型已经采用。

设计建议：演示期间两个房间由服务端持续管理，切换侧栏不停止后台另一个房间。是否在长期无人观看时停播，应由独立房间空闲策略控制，不能沿用单个观众的 20 秒租约。

## 4. 提示词竞争策略：已确认优先最新

用户已明确选择“优先最新一条，旧的未投递指令被替代，保持实时响应”。

实现语义：

- 所有被接受的消息均广播为弹幕；弹幕出现不表示模型逐条执行。
- 同一房间由服务端原子分配顺序号，以服务端接收顺序判定“最新”，不比较不同客户端的本地时钟或计数器。
- 每个房间最多保留一个尚未投递的提示词。更新到达时替换该槽位中的旧内容，记录旧事件已被替代；不存在无限提示词队列。
- 同一房间只有一个上游发送者，避免并发投递把旧内容发在新内容之后。
- 已发给 Scope 的内容无法保证撤回；只能在下一次可用投递机会发送最新内容。没有上游确认时分别记录已接受、被替代、已发送及失败，不把已发送写成画面已生效。
- 消息通过客户端消息 ID 去重；重试既不重复广播弹幕，也不把已被替代的旧消息重新排到最新。
- 断线期间的待投递内容有可配置有效期；恢复后不重放历史弹幕对应的全部提示词。

## 5. 采纳的生命周期修订

- managed Worker：仅管理本系统拥有的进程。可靠 reset 通过验证后复用；否则受控重启，再检查健康、模型就绪与历史状态清理。
- external 且具备已验证 safe_reset 的 Worker：调用并验证重置后复用。
- external 且无可靠 reset 的 Worker：会话结束后隔离；不能自动终止、重启或重新分配。恢复需要外部管理流程及验证。
- HTTP 健康检查不等于生成历史已清空。`safe_reset` 与恢复方式需要进入后续配置和适配器能力校验。
- 恢复期间 Worker 不可分配；失败进入 QUARANTINED。异步关闭响应不表示资源已经释放。

## 6. 分离超时

| 参数 | 设计语义 |
|---|---|
| HEARTBEAT_INTERVAL_S | 观众加入后立即启动心跳；开发建议 5 秒 |
| LEASE_TTL_S | 观众连接租约；开发建议 20 秒，不作为共享房间的直接停播条件 |
| SESSION_CONNECT_TIMEOUT_S | 单次观众连接建立期限；开发建议 30 秒，心跳不能无限延长它 |
| FIRST_FRAME_TIMEOUT_S | 媒体连接建立后等待可观察首帧的期限 |
| RESET_RPC_TIMEOUT_S | 单次停止/重置调用期限；开发建议 30 秒 |
| WORKER_STARTUP_TIMEOUT_S | Worker 进程启动期限 |
| PIPELINE_READY_TIMEOUT_S | 模型加载与管线就绪期限，按预实验配置 |

进程退出、启动、模型加载、就绪和最终验证分别记录耗时。所有值均为待实测配置，不是性能保证。

## 7. 远程访问与验证顺序

用户电脑访问远端 GPU 服务时，网页 HTTP 可达不代表 WebRTC 媒体可达。普通 SSH 本地端口转发提供 TCP 转发，不能据此宣称已经打通浏览器到 Worker 的 ICE 媒体路径。

先检查用户电脑与服务器之间的真实网络条件。在可达的私有网络上验证 WebRTC；若只有 SSH 通路，评估经同一 TCP 隧道转发的媒体通道等实现选项，再据实修改 MediaTransport 与验收，不默认使用外部 TURN 或开放公网端口。

建议实施顺序：

1. 在允许使用的 GPU 范围内检查占用、驱动、模型环境与目标目录；不终止他人进程。
2. 固定 Scope 版本，在一张空闲授权 GPU 上验证单路真实视频、提示词更新、速度与回收。
3. 核验同一生成任务向两个浏览器分发的行为，并选定用户电脑的媒体访问路径。
4. 完成共享房间契约、Mock、弹幕与前端侧栏，再做故障和隔离验证。
5. 配置两路真实生成，记录逐路帧率、首帧延迟、提示响应与资源占用。两路优先各用一张授权空闲 GPU，实际绑定由配置决定；不默认占满全部四张卡。

官方依据：[Scope 收视频](https://github.com/daydreamlive/scope/blob/main/docs/api/receive.md)、[参数更新](https://github.com/daydreamlive/scope/blob/main/docs/api/parameters.md)、[OpenSSH 手册](https://www.openssh.org/manual.html)。共享媒体分发与本项目远程可达性仍未实测。
